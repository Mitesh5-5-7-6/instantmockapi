# PHASE 2 UI FOUNDATION: VERCEL-INSPIRED DESIGN SYSTEM MIGRATION

Before implementing the Phase 2 Versioning + Visual Diff features, first clean up and standardize the application's entire frontend UI.

The current UI is visually inconsistent and needs a complete design-system cleanup.

Use the provided Vercel dashboard screenshot as the PRIMARY VISUAL REFERENCE for the overall visual language:

- dark developer dashboard
- clean black/dark surfaces
- subtle borders
- compact spacing
- strong typography hierarchy
- minimal visual noise
- professional developer-tool appearance
- dense but readable tables/lists
- restrained rounded corners
- subtle hover states
- small status indicators
- clean dropdowns
- clean command/search UI
- consistent buttons
- consistent toast notifications
- consistent modals
- consistent forms
- consistent navigation

IMPORTANT:

Do NOT copy Vercel branding, logos, product names, proprietary assets, or text.

Recreate the underlying visual/design principles for InstantMockAPI using the existing application's branding.

The goal is:

"InstantMockAPI should feel like a polished modern developer platform."

NOT:

"InstantMockAPI should look like a random collection of component-library defaults."

# 3. COLOR SYSTEM

Create centralized design tokens.

Use a dark-first developer-tool theme.

Example conceptual structure:

Background

- app background
- sidebar background
- panel background
- elevated panel
- hover background
- selected background

Borders

- default border
- subtle border
- strong border

Text

- primary
- secondary
- muted
- disabled

Accent

- primary action
- primary hover
- focus ring

Status

- success
- warning
- error
- info

IMPORTANT:

Do not scatter raw colors throughout JSX.

Bad:

bg-[#123456]
border-[#234567]
text-[#abcdef]

repeated everywhere.

Prefer centralized variables/tokens.

Example conceptual names:

--background
--foreground
--muted
--muted-foreground
--border
--panel
--panel-hover
--accent
--success
--warning
--destructive

Use the project's existing styling architecture if one already exists.

---

# 4. DARK THEME

The dark theme should resemble a modern developer platform.

Visual characteristics:

- near-black application background
- slightly lighter sidebar
- slightly elevated content panels
- subtle 1px borders
- restrained contrast
- white/light primary text
- gray secondary text
- bright accent only where meaningful

Avoid:

- excessive gradients
- giant glowing effects
- neon backgrounds
- excessive shadows
- excessive glassmorphism
- giant rounded cards
- excessive colors

The interface should feel engineered, not like a landing page trying to sell cryptocurrency.

---

# 5. TYPOGRAPHY

Create a consistent typography hierarchy.

Use:

- page title
- section title
- card title
- body
- secondary text
- metadata
- labels
- code/API text

Page titles should be strong but compact.

Example:

Projects

rather than:

"Welcome to your amazing API development workspace!"

Developer tools should respect the user's time.

Use monospace fonts for:

- API URLs
- HTTP methods
- endpoint paths
- JSON
- schema fields
- code
- version identifiers where appropriate

Do not use monospace for normal UI text.

---

# 6. BORDER + RADIUS SYSTEM

Use a restrained radius system.

Prefer:

- small radius for inputs/buttons
- medium radius for cards/panels
- larger radius only where justified

Do not make every element a pill.

Pills should mainly be used for:

- status
- environment
- tags
- compact filters

Most controls should use normal compact rounded rectangles.

---

# 7. BUTTON SYSTEM

Create a consistent button component system.

Required variants:

### Primary

For:

- Generate
- Create Project
- Publish
- Save
- Confirm

### Secondary

For:

- Cancel
- View
- Compare
- Open

### Ghost

For:

- icon actions
- navigation
- compact actions

### Destructive

For:

- Delete
- Remove
- destructive confirmation

### Link/Text

For:

- lightweight navigation

Every button should have consistent:

- height
- padding
- typography
- radius
- icon alignment
- hover
- focus
- disabled
- loading state

Do not create custom one-off buttons unless there is a real interaction reason.

---

# 8. ICON SYSTEM

Use ONE icon library already present in the project.

Do not mix multiple icon libraries.

Icons should be:

- small
- consistent stroke width
- aligned with text
- used to improve scanning

Do not put an icon next to every piece of text just because an icon exists.

---

# 9. TOAST SYSTEM

Standardize the entire application toast/notification system.

There must be one global toast mechanism.

Support:

Success

Example:

"Project saved"

Info

"Generation started"

Warning

"Customer API is out of sync"

Error

"Generation failed"

Loading

"Generating version..."

Toasts should have:

- consistent position
- consistent width
- consistent typography
- optional action
- dismiss behavior
- appropriate duration
- accessible announcement

Do not create custom browser alerts.

Do not create page-specific toast implementations.

Remove duplicate notification implementations where possible.

---

# 26. API ENDPOINT DISPLAY

Endpoints should have strong visual hierarchy.

Example:

Path should use monospace.

200 OK
Customer[]

[GET] /customers
[POST] /customers

[PATCH] /customers/:id
[DELETE] /customers/:id

# 27. FORM LAYOUT

Developer forms should be dense but readable.

Prefer:

Label
Description
Input

rather than giant spacing between every field.

Group related settings.

Example:

Field

Name
Type
Required
Default
Validation

Do not put every field into a separate huge card.

# 28. PAGE LAYOUT

Standard page structure:

Sidebar
│
├── Header
│
└── Main content
├── Page header
├── Toolbar
├── Main content
└── Secondary content

Use a consistent maximum content width where appropriate.

Avoid random widths on different pages.

---

# 29. RESPONSIVENESS

The design should work on:

- desktop
- laptop
- tablet
- smaller screens

The primary target is developer desktop usage.

Do not destroy the desktop experience trying to make every screen behave like a mobile marketing page.

---

# 30. ACCESSIBILITY

All standardized components must support:

- keyboard navigation
- visible focus state
- semantic buttons
- proper labels
- dialog focus management
- screen-reader-friendly status messages
- sufficient contrast

Do not remove focus outlines without replacing them with a better focus indicator.

---

# 31. ANIMATION

Use very limited animation.

Allowed:

- dropdown transition
- modal transition
- toast enter/exit
- progress transitions
- subtle hover transitions

Avoid:

- excessive page transitions
- floating elements
- decorative animations
- glowing effects

The application is a developer tool, not an amusement park.

---

# 32. DO NOT BREAK EXISTING FUNCTIONALITY

This is a UI migration.

Do NOT rewrite business logic unnecessarily.

Do NOT change:

- API contracts
- database models
- generation logic
- dependency graph
- versioning logic
- authentication
- queue architecture

unless required by the Phase 2 implementation.

Prefer replacing the presentation layer while preserving working behavior.

Modal radius = 11px

Card radius = 13px

Input radius = 7px

Badge radius = 999px

unless there is a deliberate design reason.

Create a small consistent system.
