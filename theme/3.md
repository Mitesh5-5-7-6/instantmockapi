# INSTANTMOCKAPI DESIGN SYSTEM

## Vercel-Inspired Structure + MongoDB-Inspired Green Accent

Before implementing Phase 2 Versioning + Visual Diff, establish and apply a complete visual design system across the application.

The visual direction is inspired by two products:

1. Vercel
   - black / near-black foundation
   - minimal interface
   - strong typography
   - thin borders
   - compact spacing
   - professional developer-tool aesthetic
   - restrained visual hierarchy
   - clean navigation
   - dense but readable information

2. MongoDB
   - green as the recognizable accent
   - technical/developer-oriented identity
   - green used selectively for important actions and positive states

IMPORTANT:

DO NOT clone Vercel.
DO NOT clone MongoDB.
DO NOT copy their logos, branding, text, assets, layouts, or proprietary visual elements.

Instead:

Create an ORIGINAL InstantMockAPI design system that combines:

Vercel-inspired black/minimal foundation +
MongoDB-inspired green accent +
InstantMockAPI's own developer/API identity.

The result should feel like a serious modern developer infrastructure platform.

---

# 1. PRIMARY VISUAL PRINCIPLE

The application must be:

BLACK FIRST.
GREEN SECOND.

Green is an ACCENT, not the primary background color.

The overall visual balance should approximately follow:

BLACK / DARK SURFACES
85–90%

GRAY / NEUTRAL ELEMENTS
8–12%

GREEN ACCENT
2–5%

Other semantic colors
Used only when required by meaning.

The interface should visually read as:

Dark developer platform
with
small, deliberate green highlights.

NOT:

Green dashboard with some black sections.

---

# 2. COLOR PHILOSOPHY

The color system must communicate:

Black:

- infrastructure
- developer tooling
- technical environment
- depth
- professionalism

Gray:

- hierarchy
- metadata
- borders
- secondary information
- inactive states

MongoDB-inspired green:

- creation
- generation
- success
- active state
- live API
- primary product identity

The green should immediately attract attention when it appears.

If everything is green, nothing is important.

Therefore green must be used sparingly.

---

# 3. COLOR TOKEN SYSTEM

Create centralized design tokens.

Do not scatter hard-coded colors throughout JSX/TSX/CSS.

Use semantic tokens.

Example conceptual structure:

````css
:root {
  --background: ...;
  --foreground: ...;

  --surface: ...;
  --surface-elevated: ...;
  --surface-hover: ...;
  --surface-selected: ...;

  --border: ...;
  --border-subtle: ...;
  --border-strong: ...;

  --text-primary: ...;
  --text-secondary: ...;
  --text-muted: ...;
  --text-disabled: ...;

  --accent: ...;
  --accent-hover: ...;
  --accent-muted: ...;
  --accent-foreground: ...;

  --success: ...;
  --warning: ...;
  --error: ...;
  --info: ...;

  --focus-ring: ...;
}

Use the existing project's design-token/theme architecture if one already exists.

Do not create a second competing theme system.

38. VISUAL RATIO CHECK

After implementing the theme, inspect screenshots of the major screens.

Ask:

Does the interface look predominantly black?
Is green used only where it matters?
Does green immediately attract attention?
Are normal text and borders neutral?
Are semantic errors/warnings visually distinct?
Are primary actions obvious?
Does the interface feel like a developer platform?
Is there unnecessary visual noise?
Are there too many colored elements?
Does every page look like the same product?

If green appears everywhere, reduce it.

If the interface looks completely monochrome and the brand identity disappears, increase green accents slightly.

The desired result is:

BLACK FIRST
GREEN SECOND
SEMANTIC COLORS THIRD

### The final visual formula

```text
┌──────────────────────────────────────────────────────┐
│ BLACK / NEAR BLACK                                    │
│                                                      │
│  Sidebar          Main Content                       │
│  ────────         ─────────────────────────          │
│  Projects         CRM Backend                 ● LIVE │
│  APIs             Project API                        │
│  Versions                                              │
│                   ┌──────────────────────────────┐   │
│  Generations      │ Version v5                   │   │
│                   │                              │   │
│                   │ 12 entities   42 endpoints  │   │
│                   │                              │   │
│                   │ [ Generate ]   [ Preview ]  │   │
│                   └──────────────────────────────┘   │
│                                                      │
│  Mostly BLACK + GRAY                                 │
│                                                      │
│                 GREEN GREEN                          │
│                 only where important                  │
└──────────────────────────────────────────────────────┘

The important part is not the exact hex code. The important part is the ratio and hierarchy: black owns the interface, green identifies InstantMockAPI and important actions, and red/amber/blue retain their semantic meaning.

This will also make your Phase 2 Version History + Visual Diff much cleaner because additions, breaking changes, publishing, generation, and out-of-sync states can each have a consistent visual language instead of every screen inventing its own little color civilization.
````
